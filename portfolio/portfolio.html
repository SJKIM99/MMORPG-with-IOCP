게임 콘텐츠 — 몬스터와 아이템

이후 장에서 다룰 구조가 무엇을 돌리기 위한 것인지 먼저 정리합니다. 2000 × 2000 격자 월드에 몬스터 20만 마리가 흩어져 있고, 플레이어는 이들을 잡아 무기와 물약을 얻습니다.

몬스터 — 어그로 25% · 일반 75%

  • 일반 — 시야에 플레이어가 있으면 0.5초마다 무작위로 한 칸 움직이고, 바로 옆에 붙어 있으면 반격합니다. 쫓아오지는 않습니다
  • 어그로 — 플레이어가 3칸 이내로 들어오면 깨어나, 0.5초마다 한 칸씩 추격하며 인접하면 공격합니다
  • 추격 포기 — 스폰에서 7칸 이상 벌어지거나, Zone 경계 3칸 안에 닿거나, 대상이 다른 Zone으로 넘어가면 스폰 지점으로 돌아갑니다. 몬스터가 Zone을 넘지 않으니 스레드 간 소유권 이관이 아예 필요 없습니다
  • 처치 — HP 60, 경험치 일반 3 / 어그로 5, 10초 뒤 같은 ID로 리스폰

아이템 — 물약 1종 · 무기 5종

20만 마리를 어떻게 돌리는가

① 안 보이는 몬스터는 잠들어 있다 — 20만 마리를 매 틱 순회하지 않습니다. 시야에 플레이어가 들어온 몬스터만 깨어나 타이머에 예약되고, 플레이어가 사라지면 스스로 다시 잠듭니다. 그래서 비용이 붙는 기준은 몬스터 수가 아니라 접속자 수입니다.

② A*는 마지막 수단 — 추격할 때마다 경로를 새로 계산하면 이 규모를 감당할 수 없습니다. 캐시된 경로의 다음 한 칸 → 목표 쪽으로 한 칸(그리디) → 둘 다 막혔을 때만 A* 재탐색 순으로 시도해, 장애물이 11%인 이 맵에서도 A*가 거의 돌지 않습니다.

IOCP 네트워크 계층

Windows IOCP로 수천 개의 소켓을 소수의 스레드가 처리합니다. 커널이 완료된 I/O만 알려주므로, 스레드가 소켓을 붙잡고 기다리는 시간이 없습니다.

연결 수립

  • AcceptEx로 접속 요청을 미리 등록해두고 대기
  • 수락 즉시 IOCP에 소켓을 연결하고 WSARecv 예약
  • TCP_NODELAY로 Nagle 알고리즘 해제 — 조작 반응 지연 제거

수신 처리

  • TCP는 경계가 없으므로 부분 수신을 직접 재조립
  • 패킷이 완성될 때까지 버퍼에 누적, 완성분만 처리
  • 완성된 패킷은 소유 Zone 스레드로 넘겨서 실행

Zone 분산 — 처리량 5.5배

네트워크는 병렬인데 게임 로직이 스레드 하나에 묶여 있어 4,000명에서 한계에 부딪혔습니다. 월드를 4×4로 쪼개 Zone마다 전용 스레드를 붙였습니다.

BEFORE

GameLogicThread 1개가 전 월드를 직렬 처리
→ 접속이 늘수록 큐가 밀림
→ CPU 코어를 남기고도 4,000명에서 지연 급증

▶
AFTER

월드를 16 Zone으로 분할, Zone마다 전용 스레드
→ 서로 다른 Zone은 완전히 병렬
→ 22,000명까지 안정적으로 처리

Zone 경계는 어떻게 넘나

플레이어가 Zone 경계를 넘으면 소유권을 다음 Zone 스레드로 이관합니다. 이관이 끝나기 전까지는 이동·공격·인벤토리 패킷을 모두 무시해, 두 스레드가 같은 플레이어를 동시에 건드리는 순간이 존재하지 않습니다.

이 구조가 주는 것

  • Zone 안에서는 단일 스레드 = 락이 필요 없음
  • Zone 수를 늘리면 코어 수만큼 확장
  • 이후 만든 인벤토리도 이 전제 위에서 락 없이 동작

Sector 시야 관리

"내 주변에 누가 보이는가"를 매번 전체 오브젝트를 순회해서 구하면 접속 수의 제곱으로 비용이 늘어납니다. Zone 내부를 다시 격자(Sector)로 나눠 인접한 9칸만 확인합니다.

격자가 없다면

한 명이 움직일 때마다 월드의 모든 오브젝트와 거리 비교 → 접속 수 × 오브젝트 수만큼의 연산. 1만 명이 동시에 움직이면 그 자체로 서버가 멈춥니다.

격자를 쓰면

내가 속한 칸과 인접 8칸, 총 9칸만 순회. 전체 규모와 무관하게 주변 밀도에만 비용이 비례합니다.

시야 진입 / 이탈을 알리는 방법

이동 전후의 주변 목록을 비교해, 새로 들어온 대상에게는 생성 알림을, 빠져나간 대상에게는 제거 알림을 보냅니다. Zone 경계 바깥의 Sector는 배열에 아예 존재하지 않으므로, 별도 처리 없이 Zone 경계가 자연스럽게 시야의 끝이 됩니다.

Lock-free 메모리 풀

패킷 처리 컨텍스트를 매번 new/delete 하면, 수십 개의 스레드가 힙 하나를 두고 경합합니다 — 워커만 코어 수의 두 배고, 여기에 Zone 16개와 DB 8개가 더 붙습니다. 필요할 때 만들어 붙이고, 반납받아 돌려쓰는 풀로 바꿨습니다.

문제 — ABA

직접 lock-free 스택을 짜면 ABA 문제를 만납니다. "head는 A, A의 다음은 B"까지 읽은 순간 밀려나고, 그사이 다른 스레드가 A와 B를 모두 꺼내 쓴 뒤 A만 되돌려 놓으면 — head가 여전히 A라 CAS가 성공해 버립니다. 들고 있던 "다음은 B"가 낡은 값이라 남이 쓰고 있는 B를 빈 자리로 넘겨줍니다.

해결 — Windows SLIST

OS가 제공하는 Interlocked Singly Linked List를 freelist로 사용했습니다. InterlockedPushEntrySList / Pop이 ABA를 구조적으로 차단하고, 락 없이 안전합니다.

배치 송신 — Send Queue

MMORPG는 한 사람의 행동이 주변 모두에게 알림으로 퍼집니다. 그래서 한 세션에 짧은 패킷이 몰리는데, 패킷마다 전송을 요청하면 그 횟수만큼 시스템 콜과 완료 통지가 따라붙습니다.

그냥 보내면

내 시야에 20명이 있으면, 그들이 각자 움직이고 공격할 때마다 내 소켓으로 짧은 패킷 수십 개가 따로따로 나갑니다.

모아서 보내면

전송 중이면 큐에만 쌓아두고, 끝나는 순간 쌓인 패킷을 버퍼 하나에 이어 붙여 전송 요청 한 번으로 내보냅니다.

세션당 전송은 항상 하나만

같은 소켓에 전송을 겹쳐 걸면 도착 순서가 뒤섞일 수 있습니다. 진행 중일 때는 큐에만 넣습니다.

부분 전송을 흘리지 않는다

TCP는 요청한 양보다 적게 보낼 수 있습니다. 나간 만큼만 큐에서 덜어내고, 남은 조각은 다음 배치 앞에 이어집니다.

큰 패킷이 막히지 않게

배치 버퍼가 가장 큰 서버 패킷보다 작으면 그 패킷은 영원히 못 나갑니다. static_assert로 빌드 타임에 못 박았습니다.

예약 작업 처리 — Timer Thread

체력 회복, 몬스터 이동과 리스폰, 아이템 소멸처럼 "나중에 일어나야 하는 일"을 한 스레드가 모아서 관리합니다. 몬스터가 20만 마리인 만큼, 이 스레드가 새는 비용은 그대로 전체 비용이 됩니다.

① 준비된 일은 한 번에 꺼낸다

시간이 된 이벤트를 하나씩 꺼내 처리하면 이벤트마다 락을 잡았다 놓습니다. 같은 시각에 몰린 것을 한 번에 모두 꺼낸 뒤 락을 풀고 처리합니다 — 몇 만 건이 동시에 깨어나도 락은 한 번입니다.

② 필요할 때만 깨운다

새 예약이 들어올 때마다 타이머 스레드를 깨우면, 20만 마리가 쉼 없이 예약을 넣는 상황에서 깨우는 일 자체가 부하가 됩니다. 지금 가장 이른 예약보다 빠른 것이 들어왔을 때만 깨웁니다. 그보다 늦은 예약은 어차피 자고 일어난 뒤에 처리해도 늦지 않습니다.

③ 타이머는 실행하지 않는다

시간이 됐다고 타이머 스레드가 게임 상태를 직접 건드리면 "한 오브젝트는 한 스레드" 규칙이 깨집니다. 타이머는 해당 오브젝트를 소유한 Zone 스레드로 넘기기만 하고, 실행은 그쪽에서 일어납니다.

DB 저장도 같은 형태

DB 스레드 역시 시각 기준 우선순위 큐를 쓰는 같은 구조입니다. 게임 스레드는 저장 요청을 큐에 넣기만 하고 응답을 기다리지 않으므로, DB 왕복이 게임 로직을 멈추게 하지 않습니다. 다만 "누가 먼저 처리하느냐"가 인벤토리에서는 정확성 문제로 이어졌고, 그 부분은 13장에서 따로 다룹니다.

이동 요청부터 서버 반영 통지까지의 왕복 지연을 상시 측정합니다. 지연이 기준을 넘으면 접속을 줄이고, 회복되면 다시 늘려 안정적으로 유지되는 최대 접속 수를 찾습니다.

Zone 분산까지 적용한 시점의 수치는 22,000이었고, 인벤토리 기능을 얹은 뒤 다시 측정한 값이 16,000입니다. 약 16,200에서 더 이상 늘지 않고 그 인원이 유지되는 것을 확인했습니다. 아이템 획득·사용마다 DB 쓰기가 추가된 만큼의 대가입니다.

11

인벤토리 — 설계 원칙

기능 자체는 단순하지만, 이미 만들어 둔 동시성 구조를 깨지 않으면서 얹어야 했습니다. 그 과정에서 내린 세 가지 판단입니다.

① 아이템을 전역 맵에 넣지 않는다

모든 오브젝트를 담는 전역 관리자에 아이템까지 넣으면 접속자 16,000명 기준 30슬롯 × 16,000 = 48만 객체가 들어가고, 장착·소비마다 전역 락 경합이 발생합니다.

인벤토리가 직접 소유하고, 바닥에 떨어진 아이템만 예외로 등록합니다 — 남에게 보여야 하니까요.

② 슬롯은 배열이 아닌 맵

30칸을 통째로 잡는 대신 슬롯번호 → 아이템 맵을 씁니다. 빈 슬롯은 키 자체가 없으므로 메모리도, 순회 비용도 실제 보유량만큼만 듭니다.

대신 "없는 키를 만들 수 있다"는 위험이 생겼고, 이것이 실제 결함으로 이어졌습니다 (15장).

③ 변경 즉시 DB 반영

일정 주기로 몰아 저장하면 그 사이 서버가 죽었을 때 아이템이 사라집니다. 획득·장착·소비마다 곧바로 저장 요청을 보냅니다.

단, 게임 스레드는 막지 않고 비동기로 넘기기만 합니다. 이 선택이 다음 두 장의 과제를 만들었습니다.

세 판단의 공통점 — 세 가지 모두 성능을 얻는 대신 새로운 위험을 떠안는 선택이었습니다. 전역 등록을 피해 락 경합을 없앤 대신 필드 아이템은 예외 처리가 필요했고, 맵을 쓴 대신 범위 검증 책임이 생겼으며, 즉시 저장을 택한 대신 쓰기 순서 문제가 따라왔습니다. 다음 장부터는 그 대가를 어떻게 갚았는지 다룹니다.

인벤토리 — 원자성 보장

검을 장착한 상태에서 다른 검을 장착하면 ①기존 해제 ②신규 장착, 두 가지가 함께 일어나야 합니다. 이 둘이 쪼개지면 무엇이 깨지는지부터 따졌습니다.

쪼개지면 생기는 일

  • 메모리 — "둘 다 장착" 상태가 잠깐 관측되면 공격력 계산이 틀어짐
  • DB — 두 슬롯을 따로 저장하는 사이 서버가 죽으면 한쪽만 반영된 상태가 영구히 남음

두 층 모두에서 보장

  • 메모리 — Zone 스레드 단일 소유라 함수 하나가 끝날 때까지 누구도 끼어들 수 없음
  • DB — 두 슬롯을 하나의 트랜잭션으로 저장하는 전용 프로시저를 만들어 처리

같은 원칙을 슬롯 교체에도 적용

슬롯 교체(A↔B)도 "논리적으로 한 동작"입니다. 따로 저장하면 아이템이 두 슬롯 모두에 존재하거나 어디에도 없는 상태가 DB에 남을 수 있어, 같은 트랜잭션 프로시저를 재사용했습니다.

기존에 이미 만들어 둔 기능이라도, 같은 종류의 결함이 있는지 함께 점검하고 고쳤습니다.

DB 쓰기 순서 — playerId 기반 샤딩

트랜잭션을 걸었는데도 DB가 옛날 상태로 남는 경우가 있었습니다. 원인은 트랜잭션 안이 아니라, 요청이 DB에 도달하는 순서에 있었습니다.

문제 — 꺼낸 순서와 커밋된 순서가 다르다

DB 워커 8개가 공용 큐 하나를 나눠 가졌습니다. 큐에서 꺼내는 순서는 맞지만 꺼낸 뒤에는 각자 DB 왕복을 하므로, 먼저 꺼낸 것이 먼저 커밋된다는 보장이 없습니다. 플레이어가 장착 → 해제를 빠르게 하면 "해제"가 먼저 커밋된 뒤 "장착"이 덮어쓸 수 있고, 그 상태로 서버가 죽으면 DB에는 장착된 채로 영구히 남습니다.

해결 — 같은 플레이어는 같은 샤드

Shard 0 id 8id 16id 24
Shard 1 id 9id 17
Shard 2 id 10id 18

샤드 8개, 스레드 하나가 샤드 하나를 전담합니다. 아이템 저장은 playerId % 8로 샤드가 정해지므로 한 플레이어의 쓰기는 넣은 순서 그대로 처리됩니다.

왜 하필 playerId % 8

  • 해시가 필요 없다 — playerId는 DB가 발급하는 auto-increment 순차 정수라, 나머지 연산만으로 거의 완벽히 균등하게 흩어집니다
  • 병렬성 손실이 없다 — 스레드도 커넥션도 8개 그대로, 다른 플레이어끼리는 여전히 완전 병렬
  • 줄어드는 건 "노는 워커가 아무거나 집어간다"는 유연성뿐인데, 이 쓰기는 아무도 기다리지 않는 비동기 저장이라 체감되지 않습니다
  • 자체 발명이 아니다 — Kafka가 파티션 키로 같은 키의 메시지 순서를 보장하는 것과 같은 구조입니다

함께 고친 것 · 검토한 대안

  • 교착 상태 — 같은 두 슬롯을 반대 방향으로 교체하면 서로의 행을 기다릴 수 있어, 항상 작은 슬롯 번호부터 잠그도록 순서를 고정
  • 대안 — 쓰기마다 버전 번호를 붙여 오래된 쓰기를 거부하는 방법도 있었지만, 스키마·프로시저를 모두 손대야 해서 큐 구조만 바꾸면 되는 샤드 방식을 택함

회고

이 프로젝트에서 가장 크게 남은 것은 특정 기술이 아니라, "동작한다"와 "안전하다" 사이의 거리를 재는 감각이었습니다.

병목은 재봐야 안다

네트워크를 아무리 최적화해도 로직 스레드가 하나면 소용없었습니다. 부하 테스트 도구를 직접 만들어 숫자로 확인한 뒤에야 Zone 분산이라는 답이 나왔습니다.

인벤토리를 얹은 뒤 최대 접속이 2만 2천에서 1만 6천으로 내려간 것도 같은 도구로 확인한 값입니다. 기능에는 대가가 따른다는 걸 숫자로 봤습니다.

동시성은 구조로 푼다

락을 촘촘히 거는 대신 "한 플레이어는 한 스레드만 건드린다"는 규칙을 세웠습니다. 규칙이 서니 인벤토리처럼 복잡한 기능도 락 없이 안전하게 얹을 수 있었습니다.

DB 계층에서도 같은 방식이 통했습니다. 같은 플레이어의 쓰기를 한 샤드에 몰아주는 것만으로 순서 문제가 사라졌습니다.

버그는 재현되기 전에 찾는다

쿨타임 우회도, 커밋 순서 역전도 재현된 적 없는 결함이었습니다. 코드를 다시 읽는 시간을 따로 확보한 덕분에 운영에서 만나기 전에 처리할 수 있었습니다.

고친 뒤에는 일부러 되돌려 테스트가 실패하는지까지 확인했습니다. 검증 자체를 검증하는 습관이 남았습니다.
