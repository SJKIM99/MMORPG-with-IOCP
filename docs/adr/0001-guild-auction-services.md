# ADR 0001 — 결사 · 경매장: 전용 단일 스레드 서비스 + 정산함

- 상태: 채택 (Phase 5, 2026-09-27)
- 관련: `docs/upgrade/PHASE_5.md`, `claude/UPGRADE_PROMPT.md` [Phase 5] 5-A

## 문제

결사(길드)와 경매장은 여러 Zone에 걸친 **전역 상태**다. 서버는 Zone마다 스레드 하나가 그 Zone의 플레이어 상태(그로시 · 소지품)를
락 없이 소유하는 구조이고(`ASSERT_OWNED_BY_CURRENT_ZONE`), DB 쓰기는 playerId 샤드 8개가 사람마다 넣은 순서대로 커밋한다.
여기에 다음을 만족하는 거래를 얹어야 한다.

1. 두 사람이 같은 물건을 같은 순간 사도 **정확히 한 명만** 산다. 진 쪽의 그로시는 그대로다.
2. 판매자가 오프라인이거나 다른 Zone이어도 대금이 사라지거나 두 번 들어가지 않는다.
3. 구매 도중 서버가 죽어도 재시작 뒤 **그로시 · 물건 총량이 보존**된다(복사 · 증발 0).
4. 같은 요청(`seq`)이 두 번 와도 한 번만 처리한다.
5. STRESS_TEST 봇 · 레거시 세션의 경로와 부하 조건은 그대로다.

## 선택지

| | A. 전역 뮤텍스 | B. 경매를 한 Zone 스레드에 | C. **전용 단일 스레드 서비스(액터) + 정산함** |
|---|---|---|---|
| 동시 구매 | 락 순서로 | Zone 큐 순서로 | 서비스 큐 순서로(락 없음) |
| 판매자 그로시 | 다른 Zone의 메모리를 락으로 건드림 → 소유 규칙 위반 | 판매자 Zone에 메시지 → 오프라인이면 DB 직접 → 메모리 값이 덮어씀(잃어버린 갱신) | **정산함 행** — 판매자 지갑을 건드리지 않는다 |
| 트랜잭션 범위 | 두 사람의 샤드에 걸침 | 두 샤드 | **구매자 샤드 하나** |
| Zone 부하 | 모든 Zone이 락 경합 | 한 Zone에 몰림(그 Zone의 몬스터 · 이동이 느려짐) | 서비스 스레드 따로 — Zone은 메시지 하나 |

## 결정

**C.** `GuildService` · `AuctionService`는 각자 `GameLogicThread` 하나(Zone과 같은 작업 큐)를 갖고 자기 상태만 소유한다.
Zone ↔ 서비스, 서비스 ↔ DB는 작업 큐 메시지(람다)로만 대화한다.

- **구매**: ① 구매자 Zone이 서비스에 "이 목록을 이 값에" ② 서비스가 판매 중이면 목록을 **잠금**(거래 중)하고 Zone에 알림 — 이미 팔렸거나
  거래 중이면 여기서 거절(진 쪽은 아무것도 빠지지 않는다) ③ Zone이 그로시를 확인해 메모리에서 빼고, 구매자 샤드에 **한 트랜잭션**
  `AuctionBuy`(목록이 판매 중인지 확인 · 판매됨 표시 · 구매자 그로시(절대값) · 구매자 물건 정산 행 · 판매자 대금 정산 행(수수료 뺀 값) · 시세 한 줄)
  ④ DB 스레드가 완료 콜백으로 서비스에 확정 → 목록을 지우고 판매자 · 구매자에게 알림. 그로시가 모자라면 ③에서 서비스에 잠금을 풀라고 돌려보낸다.
- **등록**: 서비스가 자리(1인 10개)와 목록 번호를 예약 → 판매자 Zone이 슬롯에서 빼고 보증금을 뺀 뒤 판매자 샤드 한 트랜잭션
  `AuctionRegister`(슬롯 · 그로시 · 목록 행) → 완료 콜백으로 서비스가 목록을 공개.
- **취소 · 만료**: 서비스가 잠근 뒤 판매자 샤드 한 트랜잭션(목록 상태 · 판매자 물건 정산 행). 만료는 1분 틱.
- **정산함 받기**: 행 하나 = 한 트랜잭션 `SettlementClaim`(행 받음 표시 · 그로시 · 슬롯) — 받는 사람 샤드. 메모리 반영은 소유 Zone이.
- **결사**: 이름 · 인원 · 직위 · 초대는 `GuildService` 메모리가 기준(이름 겹침도 여기서 판정 — DB UNIQUE는 뒷문). 세우기는
  만드는 사람 샤드 한 트랜잭션(그로시 · 결사 행 · 결사장 행), 나머지 결사 행 변경은 결사 번호 샤드(한 결사의 변경 순서 보장).
- **번호**: 목록 · 정산함 · 결사 번호는 서비스가 정한다(켤 때 DB 최댓값 + 1) — 비동기 경로에서 DB의 IDENTITY 반환을 기다리지 않는다.
- **재시작**: 켤 때(접속을 받기 전, 메인 스레드) DB에서 판매 중 목록 · 받지 않은 정산함 · 결사 · 결사원을 읽어 서비스 상태를 만든다.
  거래 중(잠금)은 메모리에만 있으므로 재시작하면 판매 중으로 돌아온다 — DB에 커밋되지 않은 구매는 없었던 일이다.
- **멱등**: 요청마다 `seq`. 소유 Zone이 사람마다 마지막 순번을 기억해 같은 순번은 두 번 처리하지 않는다. DB 쪽 두 번째 문은 상태 검사
  (판매 중일 때만 팔린다 · 받지 않은 정산함 행만 받는다).

## 결과

- 좋은 점: 락이 늘지 않는다. 동시 구매는 서비스 큐의 순서로 정해지고, 진 쪽은 그로시가 한 번도 빠지지 않는다. 모든 돈 · 물건 이동이 한 샤드 한 트랜잭션.
  판매자가 오프라인이어도 정산함에 쌓인다. 봇 · 레거시 경로는 이 코드를 지나지 않는다(확장 세션 전용 패킷).
- 나쁜 점 · 남는 위험:
  - 구매 확정까지 Zone → 서비스 → Zone → DB → 서비스로 네 번 오간다(샌드박스 기준 수 ms~수십 ms). 경매는 드문 요청이라 받아들인다.
  - ③의 트랜잭션이 **DB 오류**로 실패하면(정상 경로에서는 잠근 목록이라 실패하지 않는다) Zone이 그로시를 돌려주는 절대값 저장을 다시 넣는다.
    그 사이 같은 사람의 다른 그로시 저장(예약분이 빠진 값)이 먼저 커밋되고 서버가 죽으면 예약분이 빠진 채 남을 수 있다 —
    DB 오류 + 그 사이 다른 저장 + 서버 종료가 겹칠 때만. 실제 MSSQL에서의 발생 여부 · 대응(오류 시 재시도)은 **실기 확인 필요**.
  - 서비스 스레드 하나가 모든 경매 검색을 처리한다 — 메모리 색인이라 수천 건까지는 문제없지만, 목록이 수십만이면 검색 전용 사본(읽기 스냅샷)이 필요하다.
- 샌드박스 시험: 인메모리 DB에 커밋 일지(한 호출 = 한 줄 + fsync, 켤 때 다시 적용)를 두고, 구매 트랜잭션 안에 시험용 멈춤을 넣어 그 사이 서버를 죽인다.

## 구현하며 정한 것(2026-09-27)

- **결사 변경은 DB 먼저, 커밋되면 메모리.** 되돌리기 코드가 필요 없고 메모리 · DB가 어긋나지 않는다. 대신 세우기(만드는 사람 샤드)와 나머지(결사 번호 샤드)가
  다른 샤드라서, **한 사람의 결사 변경은 한 번에 하나**(서비스의 `_busyPlayers`)로 순서 뒤집힘(떠난 행보다 새 결사 행이 먼저 커밋)을 막는다. 한 결사의 구조 변경도 한 번에 하나.
- **머리 위 표시**는 결사 번호 · 문장만 사람마다(`User`의 atomic 두 개 — 시야 경계에서 다른 Zone이 읽는다) 두고, 이름은 서버의 읽기 전용 이름 표에서 실어 보낸다(없으면 클라가 한 번 묻는다).
- **경매 거래 거리**는 상점과 같은 규칙(경매인 곁) — 검색 · 목록은 어디서나.
- **멱등 판정은 요청을 받은 Zone에서 먼저**(서비스까지 가지 않는다). 같은 순번의 두 번째 요청은 `Duplicate`를 바로 돌려받고, 처음 요청의 결과는 따로 온다.
- **만료 틱**은 TimerThread 대신 1초 틱 스레드가 두 서비스 큐에 `Tick`을 넣는다 — TimerThread의 예약은 오브젝트(ObjID) 기준이라 전역 서비스와 맞지 않았다.
