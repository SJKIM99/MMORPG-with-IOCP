**서버 권위와의 관계 (§9)** — 지금 이동은 클라이언트 단독이다. 서버가 붙으면
`PlayerController.Intent`(이동 방향·달리기·점프)만 패킷으로 보내고 서버가
좌표를 돌려준다. 그래서 세 단계를 나눠 두었다:
`ReadIntent`(서버로 보낼 것) → `ApplyIntent`(서버도 같은 식으로 검증) → `UpdateVisual`(클라 전용).
서버 연결 시 2단계가 클라 예측이 되고, 어긋나면 3단계만 보간한다.

### 콜라이더 모양은 데이터다

`manifest.json` 의 `collider` 필드가 모양을 정한다. 값은 배율 적용 **전** 원본 단위다.

| 값 | 쓰는 곳 | 이유 |
|---|---|---|
| 없음 (기본) | 건물·벽·상자 | 메시 AABB 로 상자를 만든다 |
| `cylinder` + `radius` | 나무 19종, 가로등 | AABB 는 수관 전체(최대 13m)라 그대로 쓰면 **숲이 벽이 된다** |
| `mesh` | 성문, 던전 문틀 | 통로가 뚫린 모델. 상자로 덮으면 문이 막힌다 |

마을 콜라이더 1198개 / 필드 1059개.

### WASD 방향 버그

카메라 기준 회전 수식의 **sin 항 부호가 둘 다 반대**였다. yaw=0 에서는 맞아서
바로 드러나지 않고, 카메라를 90도 돌리면 W 가 카메라 뒤로 갔다.
사용자에게는 "카메라 회전이 반대"로 느껴졌다.

```
틀림  ( raw.X*cos - raw.Y*sin,   raw.X*sin + raw.Y*cos )
맞음  ( raw.X*cos + raw.Y*sin,  -raw.X*sin + raw.Y*cos )
```

**yaw=0 에서만 맞는 수식은 눈으로 못 잡는다.** 계산만 `RotateByCamera()` 로
빼서 카메라 4방향 × 4키 = 16건을 자동 검사한다.

### 계단을 오르지 못했던 문제

원인이 셋이었다.

1. **계단 콜라이더가 상자였다.** 기본값이 메시 AABB 라 계단 전체가 통짜 벽이 됐다.
   화면에는 계단으로 보이므로 눈으로는 구분이 안 된다. → `collider: mesh`
2. **`CharacterBody3D` 에 계단 처리가 없다.** 경사면은 `MoveAndSlide` 가 알아서
   올라가지만 계단은 수직면이라 그냥 막힌다. `TryStepUp()` 을 직접 구현했다 —
   위로 뜰 공간 확인 → 그 높이에서 전진 확인 → 내려딛을 바닥이 걸을 수 있는
   경사인지 확인. 마지막 조건이 없으면 벽을 타고 오른다.
3. **진짜로 막은 건 계단이 아니라 도로였다.** z=156~166 구간이 16% 경사인데
   포석이 4m 평면 타일이라 타일마다 0.69m 턱이 생긴다. `MaxStepHeight` 를
   0.45 로 뒀더니 계단 앞 도로에서 멈췄다. 0.75 로 올렸다 —
   캐릭터 키 2.2m 의 34% 이고, 난간(1.1m)·상자(1.05m)는 여전히 못 올라간다.

### 도로를 타일이 아니라 **지면에 칠한다** (사용자 제안 채택)

평평한 4m 타일을 경사에 놓으면 낮은 쪽 모서리가 `경사 × 타일크기` 만큼 뜬다.
실측 최대 0.94m 였고, 그 턱마다 캐릭터가 step-up 으로 순간이동했다.
타일을 2m 로 쪼개도 틈이 절반으로 줄 뿐 없어지지 않는다 — 원인이 구조적이다.

**타일 모델을 없애고 지면 자체에 포석 색을 칠한다.**
높이맵과 같은 구조의 `terrain.surface` 배열(0 = 풀, 1 = 포석)을 리전 JSON 에 넣고,
클라이언트가 정점 색으로 구워 넣는다.

| | 전 | 후 |
|---|---|---|
| 배치 수 | 2332 | **1991** (포석 341개 제거) |
| 콜라이더 | 1263 | **912** |
| 타일 틈 | 최대 0.94m | **없음** (지면 그 자체) |
| 한 틱 최대 상승(보이는 위치) | 0.352m | **0.116m** |

곁들여 지형 격자를 마을만 4m → **2m** 로 올렸다. 도로 경계가 또렷해야 하기 때문이다.

정점 색은 `VertexColorIsSrgb = true` 가 필요하다. 16진 sRGB 색을 넣었는데
기본값(선형)으로 두면 전체가 바랜다.

### 계단이 언덕에 파묻히던 문제 (사용자 제안 채택)

계단 밑 지형을 깎되 **계단 폭에 딱 맞춰** 깎아서, 바깥쪽 틀이 feather 구간에
걸려 옆구리가 묻혔다. `half_width` 를 계단 폭 + 2.5m 로 넓히고
깎는 깊이(`STAIR_CUT`)를 0.12 → 0.30m 로 키웠다.

### 씬 루트가 기울어 있던 문제 (가장 오래 헤맴)

`Client/Main.tscn` 의 루트 노드에 **약 0.6도 회전**이 저장돼 있었다.
에디터 3D 뷰포트에서 루트를 실수로 끌면 그대로 씬 파일에 남는다.

```
transform = Transform3D(0.99991816, 0.010880566, -0.0067285444, ...)
```

회전은 원점 기준이라 **멀리 있을수록 오차가 커진다.** 원점에서 130m 떨어진
광장에서 높이가 0.6m 어긋났고, 그래서 "광장 상판은 6.01 인데 플레이어가
5.40 에 서 있다" 는 모순이 나왔다. 월드 전체가 같이 기울어 렌더만 봐서는
알아챌 수 없었다.

**배치 노드의 local 과 global 을 같이 찍어 잡았다.** local 은 JSON 과 일치하는데
global 이 다르면 조상 노드에 변환이 걸린 것이다.

CLAUDE.md 5장이 "씬에 손으로 배치하지 않는다"고 못박은 이유가 이것이다 —
에디터에서 실수로 건드린 것이 데이터와 어긋나도 눈에 띄지 않는다.
`Main._Ready()` 에서 루트 변환이 단위가 아니면 경고를 남기고 되돌리도록 했다.

### 계단 콜리전을 경사면으로 (사용자 제안 채택)

계단을 trimesh 로 두면 단차마다 캡슐이 걸려 `TryStepUp` 이 발동하고,
그 한 단씩의 수직 이동이 화면에서 툭툭 튄다.

**계단 메시는 시각 전용으로 두고 콜리전은 회전시킨 상자 램프 하나로 바꿨다**
(`collider: "ramp"`). 경사면이면 `MoveAndSlide` 가 알아서 미끄러뜨려 올라가므로
step-up 자체가 필요 없다. 램프 각도·길이는 모델 AABB 에서 계산한다 —
배치 스키마는 yaw 만 갖지만, 콜라이더의 pitch 는 파생값이라 클라가 만들어도 된다.

### 3인칭 조작 2차 수정

| 증상 | 원인 |
|---|---|
| 계단이 다리처럼 3m 떠 보임 | 광장 가장자리가 수직 절벽이고 그 밖은 평지라, 계단이 평지 위에 걸쳐 있었다. 성 계단처럼 밑을 **직선 램프**로 깎고(`grade_ramp`), 램프 끝을 주변 지형에 이어 붙이는 블렌드 램프를 한 번 더 넣었다 |
| 계단에서 광장으로 못 올라감 | **계단 틀 수가 짝수**라 가운데에 틀 경계가 오고, 계단 모델의 옆 난간 두 개가 거기서 맞닿아 통행로 한복판에 벽이 섰다. `_stair_count()` 로 **항상 홀수**를 만든다 (광장 5틀, 성 3틀) |
| 캐릭터가 계속 카메라를 봄 | **KayKit 모델 앞면은 +Z 다.** Godot 기본값(-Z)으로 알고 `+ Pi` 를 더해 180도 뒤집혀 있었다. 정지 상태 초기 회전도 카메라 반대로 돌려 두었다 |
| 계단 오를 때 순간이동처럼 보임 | 몸체는 `TryStepUp` 이 즉시 옮긴다. 모델에 `_stepOffsetY` 를 두어 뒤따라오게 하고, 카메라도 몸체가 아니라 `VisualPosition` 을 따라가게 했다 |
| 점프가 낮음 | 도달 높이는 v²/2g 이므로 **2배 높이는 √2 배**다. 5.2 → 7.4 (약 0.58m → 1.16m) |

계단이 지형에 얹힌 정도: 광장 계단 최대 −0.41m(살짝 묻힘), 성 계단 +0.57m.

`--spectator` 를 추가해 플레이어 없이 자유 카메라로 찍을 수 있게 했다 —
플레이어 모드에서는 3인칭 카메라가 활성이라 `--eye/--target` 이 먹지 않는다.

### 순간이동의 진짜 원인 — 지형 기울기 임계점 (사용자 가설 적중)

사용자가 "경사면 기울기에 어떤 임계점이 있고 그걸 넘으면 순간이동한다"고 지적했고,
**맞다.** 임계점은 Godot `CharacterBody3D.FloorMaxAngle` = **52도(tan 1.28)** 다.

그보다 가파른 면은 `MoveAndSlide` 가 바닥이 아니라 **벽**으로 분류한다.
걸어 오를 수 없으니 `TryStepUp` 이 개입해 캐릭터를 한 번에 0.75m 들어 올린다 —
그게 화면에서는 순간이동이다. 도로를 지면에 칠해 타일 틈을 없앤 뒤에도
증상이 남아 있던 이유가 이것이었다.

범인은 **일부러 또렷하게 만든 대지 가장자리**였다. 광장은 3m 낙차를
격자 한 칸(2m)에 떨궈 56도, 성 언덕 치맛자락은 최대 **59도(tan 1.65)** 였다.

`terrain.py` 에 세 함수를 넣어 전수조사하고 폈다:

| 함수 | 하는 일 |
|---|---|
| `max_slope()` | 인접 격자점 사이 최대 기울기(tan) |
| `steep_cells(max_ratio)` | 한계를 넘는 지점 전부 |
| `limit_slope(max_ratio)` | 넘는 곳의 두 점을 절반씩 당겨 편다 (최대 24회 반복) |

한계는 `MAX_WALK_SLOPE = 0.84`(약 40도)로 잡았다. 52도에 딱 맞추면
격자 보간 오차로 국소적으로 넘는 지점이 생기므로 여유를 둔다.

```
마을   최대 tan 1.65(59도) -> 0.85(40도)
필드   최대 tan 1.25(51도) -> 0.84(40도)
```

처음에는 `steep_cells(0.84)` 개수로 보고해 "376 -> 377" 이 나와 실패로 보였다.
완화가 한계값 **자체로 수렴**하는데 개수는 초과(`>`)를 세기 때문이다.
보고를 `max_slope()` 로 바꿨다 — 개수가 아니라 최댓값이 의미 있는 수치다.

### 광장 높이를 계단 모서리에 맞춤

경사를 펴면 광장 가장자리가 내려앉고 계단 발치는 올라온다. 펴기 **전** 값으로
계단을 놓으면 윗단이 가라앉은 가장자리보다 솟아 "광장 둔덕이 계단보다 높다"는
모양이 된다 (사용자가 지적한 그림).

그래서 계단 배율·발치 높이를 **완화가 끝난 최종 지형에서 다시 계산한다.**
길이와 발치 높이가 등방 배율로 서로 물려 있어 두 번 돌려 수렴시킨다.

측정 결과 계단 윗단과 그 자리 지형의 차이:

```
광장 남/동/서/북 계단   diff -0.00 / -0.00 / +0.00 / +0.00 m
성 언덕 계단            diff +0.30 m  (= STAIR_CUT, z-fighting 방지용 의도된 들림)
```

**교훈: 지형 성형은 배치보다 반드시 먼저 끝나야 한다.** 배치 Y 는 배치 시점의
지형을 읽기 때문이다. 이번엔 성형 중간에 계단을 잡아 둔 것이 문제였다.

검증 (2026-09-23, `--selftest --movetest`, 실패 0건):

```
[movetest] OK  오름 연속성   한 틱 최대 상승 0.116m, 0.20m 초과 0회 (기대 0회)
[movetest] OK  남쪽 계단     도달 y=6.00 (기대 >= 5.5)
[movetest] OK  동쪽 계단     도달 y=6.00
[movetest] OK  성 언덕 경사  도달 y=10.16 (기대 >= 9.5)
```

이전에는 이 "오름 연속성" 검사가 실패했다. 한 틱 최대 상승이 0.116m 이면
걷기 4.2m/s 에 40도 경사의 이론값(약 0.059m/틱)의 두 배 안쪽이고,
`TryStepUp` 이 개입하는 0.75m 와는 자릿수가 다르다.

**주의: `--selftest` / `--movetest` 는 `--shot` 이 있어야 돈다.** 검사는
스크린샷 워밍업이 끝난 뒤 실행되도록 `_Process` 에 걸려 있어서, `--shot` 없이
돌리면 아무것도 출력하지 않고 무한정 떠 있는다.

### 자가진단이 잡아낸 것

```
godot --path Client -- --region town --selftest --shot out.png
```

레이캐스트 7종으로 "막혀야 할 곳이 막히고 뚫려야 할 곳이 뚫리는지" 본다.
눈으로는 "벽이 있다"까지만 알 수 있고 뚫리는지는 모른다.

**이 검사가 실제 버그를 두 개 잡았다.**

1. **성문이 막혀 마을을 나갈 수 없었다.** 상자 콜라이더가 문 구멍까지 덮었다.
   → `collider: mesh` 로 바꿨는데도 계속 막혔고, 파 보니 원인이 따로 있었다:
2. **성문이 도로 중심에 서 있지 않았다.** 성벽 조각 중심을
   `wall_min + step*(i + 0.5)` 로 잡아 122 와 134 에 오고, 도로 중심 128 에는
   조각 **경계**가 걸렸다. 성문이 6m 비껴 선 채 통로는 벽이었다.
   중심을 `wall_min + step*i` 로 바꿔 양 끝과 한가운데가 모두 조각 중심이 되게 했다.

지형 검사 하나는 **거짓 통과**였다 — 스폰 지점 위로 쏘아 플레이어 캡슐에 맞고 있었다.
탐침 위치를 옮겼다.

#### Godot 임포터가 노드 이름을 바꾼다 (하루를 날릴 뻔한 함정)

풍차 4개는 도는데 물레방아 3개가 안 돌았다. `.glb` 안에는 분명히
`watermill_wheel` 노드가 있는데 씬에서 찾지 못했다. 실제 트리를 찍어 보니:

```

                     (씬루트)   (glTF루트)  (바퀴, 원래 watermill_wheel)
```

**Godot 의 씬 임포터는 노드 이름의 접미사를 예약어로 해석해 노드 타입을 바꾸고
그 접미사를 이름에서 떼어낸다.** `-col`, `-convcol`, `-rigid`, `-vehicle`,
`-wheel`, `-navmesh` 등이고 **하이픈뿐 아니라 밑줄도 인식한다.**
`watermill_wheel` 이 `_wheel` 에 걸려 `VehicleWheel3D` 로 바뀌고 이름이
`watermill` 이 된 것이다. `mill_blades` 는 예약어가 아니라 멀쩡했다.

떼어낸 이름으로 다시 찾되 **가장 깊은 일치**를 고른다 — 얕은 것부터 고르면
맨 위 루트가 걸려 건물 전체가 돌아간다.

### 물 — 개울 / 강 / 호수 / 폭포 (2026-09-23)

**물 타일은 쓰지 않았다.** 팩의 물은 전부 헥스 타일(전략맵용)이라 도로 타일과
똑같이 경사에서 뜬다. 지형을 파고 셰이더로 덮었다.

| | 내용 |
|---|---|
| 지형 | `terrain.carve_channel()` — 꺾은선을 따라 파고 `water[]` 에 수면 높이를 적는다 |
| 마을 | 서쪽 x≈62 를 따라 북에서 남으로 흐르는 개울. 지형이 실제로 2.9m -> -0.6m 로 내려가는 축이라 억지로 판 것이 아니다 |
| 물레방아 | 뒷골목에 흩어 놓던 것을 **개울가로 옮겼다.** 물 없이 도는 물레방아가 제일 어색했다 |
| 다리 | 대로가 개울을 건너는 z=128 에 `prop_bridge` 3틀 (모델이 Z 로 4.5m 라 도로 폭 12m 를 채우려면 3틀) |
| 폭포 | 물레방아 둑. 격자 한 칸(2m)에 3m 를 떨궈 **56도** |
| 필드 | 북쪽 구릉에서 내려와 가운데 분지(-9m)의 호수로 들어가는 강. 중간에 급류 |
| 내비 | `water.nav = "exclude"` — **Week 2 Recast 빌드가 읽는다**. 내비메시가 무언가를 증명하려면 통과 못 하는 영역이 실제로 있어야 한다 |

#### 물을 경사 정리 **뒤에** 파는 이유

`limit_slope` 를 먼저 돌리면 판 물길이 도로 펴져 메워진다. 그래서 물길은 맨 끝에
판다. 대신 거기서 만든 경사는 아무도 검사하지 않으므로 `depth / bank` 비율로
**직접** 한계 아래를 보장해야 한다. 둑 폭이 그 유일한 손잡이다 —
5.0m 로 뒀더니 걸을 수 있는 곳의 최대 경사가 47도까지 올라가서 7.5m 로 넓혔다.

```
마을  걸을 수 있는 곳 최대 tan 0.91 (42도)   / 한계 52도
      물속(폭포)        최대 tan 1.51 (56도)   ← 일부러 넘긴 것
필드  걸을 수 있는 곳 최대 tan 0.84 (40도)
```

#### 폭포를 56도로 **일부러** 넘긴 이유

step-up 한계가 0.75m 다. 위험한 것은 0.2~0.75m 의 애매한 턱이고, 그건 step-up 이
성공해서 캐릭터를 순간이동시킨다. 3m 벽은 올라갈 수 없으니 그냥 막힐 뿐이고,
떨어지는 것은 막히지 않으므로 하류로는 그대로 흘러내려간다.

필드에서는 같은 짓을 할 수 없다 — **격자가 8m 라 수직 낙차가 한 칸에 담기지
않는다.** 16m 구간에 6m 를 떨군 20도 급류로 대신했다.

### 굴뚝 연기

굴뚝 노드는 존재하지 않는다. KayKit 건물은 **머티리얼별로** 프리미티브가 나뉘어
있고 부위별이 아니다. 대신 이 성질을 썼다 —
**굴뚝은 석재인데 지붕(Brown)보다 높이 솟은 유일한 부위다.**

`tools/find_chimneys.py` 가 찾아 manifest 에 적는다. 런타임에 메시를 뒤지면
그건 코드고, 한 번 찾아 적어 두면 데이터다(5장).

```
bld_house_a   굴뚝 1개  로컬 (0.378, 0.905, -0.401)  월드 (2.27, 5.43, -2.41)
```

어느 집에 불이 지펴져 있는지는 **배치 데이터**가 정한다(`smoke: true`, 37채 중 15채).
manifest 의 chimney 는 모델의 성질이고 smoke 는 배치의 성질이라 층위가 다르다.

### 물과 연기에서 나온 함정 넷

전부 "화면이 이상한데 원인이 다른 층위에 있는" 유형이었다.

1. **정점 색은 RGBA8 로 저장되어 0~1 로 잘린다.** 수심을 미터로 넣었더니 1m 를
   넘는 순간 전부 1.0 이 되어 깊이 정보가 사라졌다. `max_depth` 로 나눠 넣고
   셰이더에서 되돌린다.
2. **물가 밖 한 칸에도 수면을 칠해 수심이 음수가 되었다**(실측 -6.4m). 셰이더는
   수심 0 을 물가로 보고 거품을 칠하므로, 격자가 8m 인 필드에서는 그 거품 띠가
   호수의 절반을 덮었다. `_drain()` 으로 지형보다 낮은 수면을 지운다.
   거품 구간 22% -> 5%.
3. **거칠기 0.18 짜리 수면은 하늘을 통째로 반사한다**(프레넬). 물리적으로 맞지만
   호수가 새하얗게 떠서 물색이 사라졌다. 0.45 로 올렸다.
4. **파티클이 부모 배율 6 을 물려받아 속도와 중력까지 6배가 되었다.** 연기가
   20m 넘게 치솟아 굴뚝에서 끊겨 보였다. `Scale = One / scale` 로 상쇄한다 —
   `CollisionBuilder` 가 콜라이더에 쓰는 것과 같은 수법이다.
   그리고 입자 크기 = 메시 반지름 x Scale x ScaleCurve 로 **셋이 곱해진다.**

1~3 은 눈으로 구분할 수 없어서 **셰이더가 수심·흐름·거품을 RGB 로 출력하게
바꿔** 한 장 찍고 끝냈다. 빨강=깊이, 노랑=급류, 흰 점=거품이 정확히 나와서
데이터는 멀쩡하고 조명 문제라는 것이 그 자리에서 드러났다.
(`fragment()` 에서는 `return` 을 쓸 수 없다. 맨 끝에서 덮어써야 한다.)

### 수면이 공중에 떠 있던 문제 (사용자 지적)

물이 잔디 위에 얹힌 판자처럼 보였다. 가장자리를 재 보니 **중앙 0.84m,
최대 3.64m** 떠 있었다.

원인은 수면 마스크를 좁게 칠한 것이었다. `half_width + cell` 까지만 칠했는데,
둑은 그보다 훨씬 밖에서 수면과 만난다. 다리 자리 단면으로 확인:

```
x=50  지형 0.70   <- 여기가 진짜 물가 (수면 0.62 와 만난다)
x=54  지형 0.04   <- 아직 물속인데
x=56  지형 -0.31  수면 0.62   <- 수면은 여기서 끊겼다. 0.93m 공중
```

고친 방법은 도로를 지면에 칠한 것과 같은 발상이다:

1. **둑 끝까지** 수면을 칠한다.
2. 지형을 다 만진 뒤 `finish_water()` 를 **한 번만** 부른다.
   지형보다 낮은 수면을 지우고, 물에 닿은 마른 점을 **한 줄 남긴다.**

그 한 줄이 핵심이다. 마지막 사각형이 물속에서 땅속으로 관통하며 끝나므로,
눈에 보이는 물가는 **수면과 지형이 만나는 선**에 저절로 생긴다.

물가 줄을 지형 높이로 끌어올려 봤다가 되돌렸다. 다리 교대처럼 물가가 수직인
곳에서 물이 벽을 타고 올라 **2m 벽에 0.9m 짜리 가짜 폭포**가 생겼다.
수면은 수평이어야 한다. carve_channel 이 적어 둔 값을 그대로 두고 지형이
덮게 하는 것이 맞다.

```
마을   가장자리 252점, 지형 위로 뜬 것 0개
필드   가장자리  72점, 지형 위로 뜬 것 0개
```

### 다리를 건널 수 없던 문제 (사용자 지적)

점프해도 못 올라갔다. 상판을 그냥 수면 + 0.35m 에 얹어 도로보다 1.5m 높았다.

glTF 정점을 직접 재서 통행로(|z| < 1.5) 단면을 뽑았다:

```
끝 -0.15 -> 0.23 -> 0.80 -> 가운데 1.66   (배율 6 적용, 원점 기준)
```

도로와 맞춰야 하는 것은 **끝(-0.15)** 이지 최고점(1.66)이 아니다. 최고점은
아치 꼭대기다. 난간은 없다 — |z| >= 1.5 에서도 최고가 1.66 으로 같다.

고친 방법은 둘이다:

1. **도로를 상판 높이까지 돋운다** — 실제 다리의 교대(abutment)와 같다.
   상판 끝 = 수면 + 0.9m 로 잡고, 원점 높이를 역산한다.
2. **콜라이더를 `mesh` 로 바꾼다.** 상자로 두면 아치 아래가 막히고 상판 경사도
   사라져 12 x 4.7 x 4.5m 짜리 통짜 블록이 된다 — 성문과 같은 문제였다.

#### grade_ramp 가 개울을 메웠다

둑을 `grade_ramp` 로 돋웠더니 폭 10m 개울이 **2m 로 졸아들었다.**

`grade_ramp` 는 점과 선분의 거리로 판정하므로 모양이 **캡슐**이다 — 양 끝에서
half_width 만큼 더 번진다. 계단에서는 그게 이득이었지만(끝을 주변 지형에 이어
붙여 준다) 도로를 깎을 때는 재앙이다. half_width 7.6m 짜리 캡이 개울
한복판까지 뻗었다.

진행 방향으로도 경계를 두는 `grade_ramp_span()` 을 새로 만들고, 앞뒤 feather 를
따로(0.6m) 줬다. 옆으로는 부드럽게 퍼지되 앞뒤로는 바짝 끊어야 하기 때문이다.

```
x=56  지형 1.52  <- 다리 끝 (교대)
x=58  지형 -0.48  수면 0.62
x=66  지형 -0.49  수면 0.61   <- 개울 폭 그대로
x=68  지형 1.52  <- 다리 끝
```

교대 벽이 2m 수직이지만 상판 아래에 가려 보이지 않고, 0.75m 를 훨씬 넘으므로
step-up 이 발동하지 않는다.

#### 걸어서 확인한다

`CheckBridge` 를 movetest 에 추가했다. 상판 높이는 지형·수면·모델 치수가
맞물려 나오므로 하나만 어긋나도 조용히 다시 벽이 된다.

```
[movetest] OK  다리 건너기  x 48.0 -> 77.2 (기대 >= 74), y 2.11 (기대 >= 1.0)
```

y 도 함께 본다. x 만 보면 개울에 빠져 바닥으로 걸어 건너도 통과한다.

#### movetest 는 마을 전용이다

필드에서 돌렸더니 4건이 실패했고 y 가 **-846** 이 나왔다. 검사 좌표가 전부
마을 것(광장 계단, 성 언덕, 개울 다리)이라 허공에서 출발해 월드 밖으로
떨어진 것이다. 리전 ID 를 받아 건너뛰되, **건너뛴다고 찍는다** — 조용히
통과시키면 검사가 있는 줄 알고 방심한다.

### 수면에 구멍이 뚫려 보이던 문제 (사용자 지적)

물 사이로 바닥이 들여다보였다. 세어 보니 **49칸**이었고 원인은 한 줄이었다.

`finish_water()` 의 물가 줄을 **4방향 이웃**으로만 찾았다. 그런데 클라이언트는
네 꼭짓점이 **모두** 물일 때만 사각형을 그린다. 대각선으로만 물에 닿은 점은
물가 줄에서 빠지고, 그 점을 모서리로 갖는 사각형이 통째로 안 그려진다.

```
대각선으로만 물에 닿아 물가 줄에서 빠진 점: 48개  ->  구멍 49칸
```

8방향으로 바꿔 0 이 되었다. 그리는 쪽(WaterMesh)과 만드는 쪽(finish_water)의
**연결 규칙이 달랐던 것**이라, 어느 한쪽만 보면 찾을 수 없는 유형이다.

검사를 양쪽에 붙였다 — 생성기는 `water_holes()` 를 찍고, 클라는 실제로
건너뛴 칸을 세어 `WaterMesh.SelfTest` 로 확인한다.

처음에는 클라 쪽이 298칸을 보고해 당황했다. 판정 기준이 달랐다 — 물가 줄은
지형 **아래**에 잠긴 채 값만 가지고 있어서, "물 값이 있다"로 세면 물 밖의
칸까지 구멍으로 잡힌다. "실제로 잠겼는가"로 맞추니 0 이 되었다.

### 물이 넓게 범람하던 문제

성벽 자리에서 **수면 6.33m, 지형 2.79m** — 물이 3.5m 깊이로 넓게 퍼져 있었다.

꺾은선 꼭짓점이 z=18 과 z=58 두 개뿐이라, 수면은 그 사이를 **직선으로**
내려오는데 지형은 훨씬 빨리 떨어진다. 중간(z=32)에서 수면이 지형을 3.6m
앞질러 골짜기를 벗어났다.

```
        z=16   z=22   z=28   z=34   z=40
고치기 전 수심  1.10   1.38   3.13   3.02   2.46   <- 골짜기를 넘쳤다
고친 뒤   수심  1.10   1.10   1.10   1.10   1.10
```

꺾은선을 6m 간격으로 잘게 나눈 뒤 수면을 계산하게 했다(`_densify`).

여기서 두 번째 버그가 따라 나왔다. 잘게 나누면 **원래 3번 꼭짓점이 더 이상
3번이 아니다.** 그걸 잊고 `stream[3]` 을 다리 자리로 쓰는 바람에 다리가 상류의
수면을 읽어 1.52m 여야 할 상판이 3.18m 가 되었다. 원래 꼭짓점의 새 인덱스를
함께 돌려주도록 고쳤다.

### 물길이 성벽을 뚫고 지나던 문제 (사용자 지적)

성문 아치를 재 봤더니 통로가 **5.2m** 라 폭 10m 개울이 들어가지 않는다.
벽을 물 아래까지 늘리면 개울을 막아 버린다.

그래서 **개울에 걸치는 성벽 조각을 빼고 양옆을 감시탑으로 마감했다.**
강이 곧 방벽이 되는 배치는 실제 축성에서도 흔하고, 탑으로 끝을 막으면
"무너진 곳"이 아니라 "일부러 낸 수문"으로 보인다. 새 에셋이 필요 없다.

```
성벽 조각 68 -> 직선벽 56 + 성문 4 + 감시탑 8 (모서리 4 + 수문 양옆 4)
물에 잠긴 성벽 조각: 0
```

#### 덤으로 나온 것 — 모서리마다 벽 두 조각과 탑이 겹쳐 있었다

탑 위치를 재다 발견했다. 네 모서리에서 **가로줄 벽·세로줄 벽·감시탑이 정확히
같은 좌표(거리 0.0m)** 에 있었다. 탑을 뚫고 나온 흰 벽이 그것이다.
`wall_run` 이 i=0 과 i=count 를 모두 놓아 두 줄이 모서리에서 겹친 탓이다.

양 끝을 건너뛰게 했다. 탑 반경 5.28m 에 첫 조각이 6.0m 앞에서 시작하므로
틈이 0.7m 남는데, 캐릭터 캡슐 지름이 0.84m 라 빠져나갈 수 없다.

### 수면이 바둑판처럼 보이던 문제

값 노이즈는 정사각 격자 위에서 만들어지고, **값은 부드러운데 미분이
불연속**이다. 법선은 미분에서 나오므로 격자 경계마다 각이 지고 반사가 그 각을
그대로 드러낸다. 노이즈 값만 찍어 보면 멀쩡해서 원인을 찾기 어려운 유형이다.

옥타브 4개를 겹치고(FBM) 매 옥타브를 35도씩 돌렸다. 하늘 셰이더에서 구름에
쓴 것과 같은 수법이다.

### 남은 한계

- 이동 권위가 클라이언트에 있다. 서버가 붙기 전까지 임시다.
- 공격 애니메이션이 없어 Idle / Walk / Run / Jump 만 쓴다 (FREE 티어 제약).
- NPC·몬스터에 콜라이더가 없다. 통과한다.

## 월드 배치

**서버와 클라가 같은 JSON 을 읽는 구조가 실제로 돌아간다** (§5).
`world/regions/*.json` 이 유일한 진실이고, Godot 씬에는 오브젝트를 하나도 손으로 놓지 않았다.
조명·환경·카메라까지 코드로 만든다.

| 리전 | 크기 | 배치 | NPC | 지형 | 비고 |
|---|---|---|---|---|---|
| `town` | 256² | 2323 | 13 | 65² / −1.1~19.8m | 사각 광장(48m)+우물+노점+난간, 4방향 진입 계단, 성 언덕, 건물 90여 채, 십자 포석 대로, 성벽 밖 밀밭·구릉 |
| `field_01` | 512² | 1679 | 0 | 65² / −11.2~27.8m | 구릉·분지, 스폰 4곳(몬스터 27), 엘리트 순찰 경로, 언데드 구역 고사목 |

**재현성 확인** — 두 번 생성해 SHA256 이 동일함을 확인했다. seed 는 리전별로 분리해
한쪽을 고쳐도 다른 쪽 배치가 흔들리지 않는다.

### 지형 (schema_version 2)

높이맵을 리전 JSON 안에 **샘플링된 배열로** 넣는다 (`terrain.cell` / `resolution` / `heights`,
row-major, `index = iz * resolution + ix`). 생성 함수를 저장하고 양쪽에서 다시 계산하면
Python / C# / C++ 의 부동소수점 차이로 갈라질 수 있다. 배열은 갈라질 여지가 없다.

- `tools/terrain.py` — `Bump`(구릉) / `Plateau`(원형 대지) / `BoxPlateau`(사각 대지) 합성
- 대지 높이는 절대 표고가 아니라 **주변 지형 대비 상승량**이다. 절대값으로 두면
  바탕 지형이 올라갈 때 광장이 웅덩이가 된다.
- `grade_corridor()` — 도로 노반을 깎는다. 이걸 안 하면 경사면에서 타일마다
  지형에 물려 4m 간격으로 검은 줄이 생긴다.
- `Client/World/TerrainMesh.cs` — 같은 배열로 지면 메시를 만든다. 쌍선형 샘플링 식이
  Python 쪽과 동일하다.

**계단은 배율을 데이터에서 역산한다.** manifest 의 고정 배율을 쓰면 지형이 바뀔 때마다
계단 위가 뜨거나 아래가 묻힌다. `fit_stairs(bottom_y, top_y)` 가 실제 단차를
`tile_stairs_long` 의 원본 상승(5.10m)으로 나눠 배율을 정하므로 항상 정확히 걸친다.

### 배율 문제와 해결

Medieval 팩은 전략맵 비율이라 일괄 배율로 맞출 수 없었다. 집 1.69 : 우물 1.02 인데
실제 비는 약 5:1 이다. ×6 을 걸면 우물이 6.1m 가 되어 집의 절반이 된다.
`bld_well` 만 3.2, 나머지 `bld_*` 는 6.0 으로 분리했다.
`bld_mill`·`bld_watermill` 은 원점이 바닥이 아니어서(min.y < 0) `y_offset` 을 넣었다.

던전 팩 소품은 반대로 캐릭터(2.2m)보다 크다 — 통이 2.0m 다. `prop_barrel_*` 등은
0.7 로 낮췄고, 원래 사람 크기인 의자·걸상·탁자는 1.0 을 유지했다.

### 접지 검사 (2026-09-22)

F5 로 돌아다니다 "건물이 공중에 떠 있다" 는 지적을 받고 **배치 y 와 지형 높이를
전부 대조하는 스크립트**로 원인을 찾았다. 눈으로 찾을 수 있는 양이 아니었다.

| `tile_stairs_long` 4개 부양 / 15개 최대 −2.29m 매몰 | 평면 계단을 경사 한가운데 놓았다 | 발치를 먼저 평탄화(`grade_flat`)하고 배치 |

놓는 시점의 지형에서 뽑으므로, 나중에 지형을 건드리면 이미 놓인 것이 뜨거나 묻힌다.

### 2차 검수 (2026-09-22) — 회전과 접지

F5 로 직접 돌아다니며 받은 지적을 하나씩 좌표로 확인해 고쳤다.

| 증상 | 원인 |
|---|---|
| 광장 난간이 빗살처럼 꽂힘 | 난간은 X축이 긴데 `yaw = atan2(ux, uz)` 를 써서 90도 틀어졌다. 로컬 +X 는 `(cos yaw, -sin yaw)` 를 향하므로 `atan2(-uz, ux)` 가 맞다 |
| 노점 탁자도 변에 수직 | 탁자는 Z축이 긴 쪽(2×4m)이라 `atan2(ux, uz)` 가 맞다 |
| 계단 폭이 5.9~17.4m 로 제각각 (도로는 12m) | 등방 배율이라 상승 높이가 폭까지 바꾼다. **개수**를 계산해 폭을 맞춘다 |
| 도로가 얼룩말 무늬 | 5% 경사에서 타일을 발자국 **최저점**에 맞춰 오르막 모서리가 묻혔다. 얇고 평평한 타일은 **최고점** 기준이 맞다 (내리막에 몇 cm 턱이 남지만 훨씬 낫다) |
| 대로가 성 언덕 58% 사면을 넘어감 | 대로를 성 계단 앞에서 끊었다 |
| 동·서 계단 경사로가 광장 **안쪽**으로 내려감 | 네 방향 yaw 를 손으로 적다가 동/서 부호를 뒤집었다. `yaw = atan2(dx, dz)` 로 계산한다 |
| 북쪽 계단 발치가 0.73m 묻힘 | 성 언덕이 땅을 밀어올려 단차가 1.5m 뿐 → 계단 길이 2.36m 로 격자 한 칸(4m) 보간 구간을 못 덮었다. 네 발치 높이를 광장 설계 높이(−3.0m)로 통일해 계단 4개를 동일하게 만들었다 |

**가장 오래 걸린 것은 `grade_flat(feather=0)` 이 아무 일도 하지 않던 버그다.**
`_smoothstep(0, 0, 0)` 이 1 을 돌려주어 가중치가 0 이 되고, 광장 상판 재평탄화가
통째로 무효였다. 그래서 광장 가장자리가 5.98 이어야 할 자리에서 5.10 으로
주저앉아 있었고, 그 위에 깔린 포석이 잔디에 묻혔다.
경계값(feather = 0)을 따로 처리해 해결했다.

**결과: 마을·필드 모두 부양 0 / 매몰 0, 포석 309개 중 가려짐 0개.**
(계단은 원점이 윗단이라 이 검사로 재면 거짓 양성이 난다 — 윗단·발치를 따로 대조했다.)

| 직선 계단 ↔ S자 치맛자락 최대 1.34m 어긋남 | `grade_ramp()` 로 계단이 놓일 띠만 직선으로 깎았다 → 0.48m |
| 난간만 보이고 디딤판이 잔디에 먹힘 | 계단면과 지형이 정확히 같은 높이라 z-fighting. 램프를 12cm 낮춰 계단을 띄웠다 |
| 위병이 계단에 등을 돌림 | `yaw = 0` 은 모델이 -Z(북)를 본다. 오르는 사람을 마주보려면 `math.pi` |
| 마을 주민이 성 꼭대기에 홀로 서 있음 | 대로변 주민을 `mid ± 52~58` 에 뒀는데 북쪽 하나가 성 언덕 위로 올라갔다. 주민 8명을 광장 노점 앞으로 옮겼다 |
| 상인이 서쪽 계단 발치에 끼어 있음 | 상점이 서쪽 대로 한복판이었다. 광장 북서쪽 모서리 바깥으로 비켰다 |

`Heightmap` 에 `grade_ramp`(직선 경사로)와 `grade_disc`(원형 대지 재고정)를 더했다.
**대지를 깎은 뒤에는 반드시 상판을 다시 고정해야 한다** — 광장은 `grade_flat`,
성 언덕은 `grade_disc` 로 같은 처리를 한다.

### 계단과 성 언덕이 겹쳤던 문제

성 언덕을 z=78 에 두자 치맛자락(110)이 광장 치맛자락(100)과 10m 겹쳐
**성 계단(z=103.5)과 광장 북쪽 계단(z=102)이 1.5m 간격으로 포개졌다.**
성 언덕을 z=62 로 밀어 두 대지 사이에 평지를 남겼다.

원점을 광장 가장자리에 놓아야 윗단이 광장과 맞물린다.

### 순서를 이렇게 정한 이유

앞 작업이 뒤 작업을 깨지 않게 하려면 **아래에서 위로** 쌓아야 한다.

1. **타입 먼저.** 좌표 타입을 바꾸면 그 타입으로 쓴 코드가 전부 무효가 된다.
2. **데이터 먼저, 그걸 쓰는 로직은 나중.** 리전 크기를 모르고 Sector 를 재편하면
   256 을 하드코딩했다가 다시 뜯는다.
3. **프로토콜을 클라이언트보다 먼저 확정.** 패킷이 바뀌면 직렬화기를 다시 쓴다.
4. **매 단계 빌드가 살아 있고 STRESS_TEST 가 돈다.** 이게 "뒤 작업이 앞 작업을
   깼는지" 알아내는 유일한 수단이다.

코드를 다시 건드리지 않는다 — 포탈은 트리거와 클라 씬 교체만 남는다.

### 1번 완료 — `Vec3` 도입 + `Transform` 3D화 (2026-09-23)

브랜치를 `godotclient` 로 옮기고 여기서만 작업한다.

| 바뀐 것 | 내용 |
|---|---|
| 새 타입 | `GameServer/Transform/Vec3.h` — `struct Vec3 { float x, y, z; }` + XZ 거리 |
| `Transform` | `short m_x, m_y` -> `Vec3 m_pos` + `float m_yaw`. 섹터 인덱스는 `m_sectorX/m_sectorZ` |
| 축 이름 | `ZoneCoord`, `SectorCoord`, `ZoneLayout`, `Sector` 의 두 번째 축을 전부 Y -> Z |
| 월드 좌표 타입 | `Sector`, `SectorHelper`, `ZoneManager` 의 월드 파라미터를 `short` -> `float` |
| 파일 | 21개 수정 + 1개 추가, +319 / -253 줄 |

#### 옛 `GetY()` 를 **삭제**한 이유

2D 시절의 `m_y` 는 높이가 아니라 **지면의 두 번째 축**이다. 이름만 두고 뜻을
바꾸면 놓친 호출부가 조용히 컴파일되면서 틀린다. 그래서 `GetY/SetY/RefY` 를
지우고 `GetZ/SetZ/RefZ` 를 넣어 **모든 호출부가 컴파일 에러로 드러나게** 했다.
새 `GetY()` 는 높이지만, 이름이 같아도 뜻이 달라 한 번은 반드시 눈으로 보게 된다.

컴파일러가 실제로 전부 찾아냈다 — 첫 빌드에서 SectorHelper / ItemHelper /
MonsterHelper / UserHelper / Zone 의 호출부가 줄줄이 떴다.

#### 암묵 절단 122건을 명시적 경계 33건으로

타입만 바꾸고 나니 **C4244(float -> short, 데이터 손실) 경고가 122건** 떴다.
그대로 두면 어디가 의도한 절단이고 어디가 실수인지 구분할 수 없다.

`ToLegacyTile()` 하나를 만들어 전부 그 문을 지나게 했다. 아직 정수 좌표를
요구하는 곳은 두 군데뿐이다:

1. **패킷** — `SUBJECT_MOVE_NFY` 등이 `short x, y` 를 보낸다 (교체는 5번 단계)
2. **타일 격자** — A* / Collision / 인접 판정 (교체는 Week 2 의 Recast)

옛 월드에서는 1타일 = 1좌표 = 패킷 단위라 셋이 같은 값이었다. 나중에 이 함수를
지울 때 고쳐야 할 자리가 그대로 목록이 된다.

```
경고 122건(암묵) -> 0건.  ToLegacyTile 명시 호출 33곳.
```

#### 이 단계에서 **일부러 바꾸지 않은 것**

월드 크기(2000x2000)와 **패킷 레이아웃**. 그래야 기존 STRESS_TEST 가 그대로
돌아 회귀 검증이 된다. 실제로 STRESS_TEST 는 **소스 한 줄도 고치지 않고**
0 오류 / 0 경고로 빌드됐다 — 프로토콜 경계가 지켜졌다는 증거다.

높이(`m_pos.y`)도 아직 아무도 쓰지 않는다(정적 확인: `SetY`/`m_pos.y` 쓰기 0건).
지형 높이 샘플러가 들어오는 4번 단계부터 채워진다.

#### 검증

축 스왑은 월드가 정사각형이라 크래시 없이 조용히 틀린다. 세 겹으로 확인했다.

1. **diff 전수 확인** — 좌표 두 개를 넘기는 모든 줄이 `(X, Z)` 순서인지 눈으로 대조
2. **풀 솔루션 재빌드** — 0 오류 / 0 경고
3. **봇 1468마리 실제 구동** (Debug 빌드)

```
Active 1468 / Dead 0        Zones Z01~Z16 각 86~103 (고르게 분포)
Monsters Known 14321, Dead 1265     Items Picked 243
Visibility  Monsters 11.9 / Players 0.1
```

Zone 분포가 고르다는 것은 `GetZoneIdByWorld(float, float)` 가 맞게 계산된다는
뜻이고, 몬스터를 보고 죽이고 아이템을 줍는다는 것은 시야(Sector AOI)와
인접 판정(`ToLegacyTile` 경유)이 전과 같이 동작한다는 뜻이다. 축이 바뀌었다면
Zone 분포가 쏠리거나 전투/줍기가 실패했을 것이다.

**측정하지 않은 것:** 같은 날 기준선이 없어 성능 회귀 여부는 말할 수 없다.
지연 182ms(최대 633ms)는 Debug 빌드 1468봇 값이고, 제대로 된 기준선은
9번 단계에서 잡는다.

### 이번 주에 하지 않는 것

Recast/내비메시, 몬스터 FSM, 인던, 리전 간 포탈(구조만 열어 두고 기능은 Week 2),
**클라 예측(prediction)**. 8번은 "서버 위치를 보간해 표시"까지만 한다 —
예측을 먼저 넣으면 서버 검증 버그와 예측 버그가 섞여 원인 분리가 안 된다.

## 알려진 미해결 / 주의

- **공격 애니메이션이 없다.** KayKit FREE 티어 `Rig_Medium` 26클립에 공격 모션이 없다
  (`Hit_A/B` 피격, `Death_A/B` 사망만 존재). FSM Combat 상태에서 재생할 클립이 없다.

  `world/manifest.json` 의 `animation_libraries.$missing.attack` 참조.

- **Medieval Builder Pack은 걸어다니는 마을 키트가 아니다.** hex/square 격자 전략맵용
  미니어처다 (`house` 실측 1.69 × 0.91 × 1.66 m, 캐릭터는 2.17 m).
  `bld_*` 9개 엔트리에 `scale: 6.0`을 넣었으나 **전부 `scale_verified: false`** —
  실측값에서 역산한 제안값이고 Godot에서 렌더해 확인하지 않았다. Week 4에 확정.

- **KayKit Character Animations 1.2 는 사용하지 않는다.** 리그가 구버전(노드 8개)이라
  Adventurers/Skeletons 의 `Rig_Medium`(본 23개)과 본 구조가 다르다. 30개 클립 적용 불가.
  `assets/vendor/kaykit_animations/` 에 받아둔 채로 두되 `manifest.json` 에서
  `status: unused` 로 표시했다.

- **압축 해제 사고 1건.** Medieval 팩이 Character Animations 의 `License.txt` 를
  같은 경로에서 덮어썼다. 덮어쓰기 전 읽은 내용을
  `assets/vendor/kaykit_animations/LICENSE_NOTE.md` 에 "복원이 아니라 옮겨 적은 것"으로
  명시해 남겼다. README 에 재발 방지 경고 기재.

  불필요. Week 4에 1K로 축소. `glTF/` 폴더 안에 같은 PNG 사본이 또 있어 현재 중복 보관 중.
