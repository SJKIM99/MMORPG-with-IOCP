IOCP 기반 MMORPG 게임 서버 정리

이 문서는 제가 직접 설계하고 구현한 IOCP 기반 MMORPG 서버를 정리한 문서입니다. 네트워크 완료 처리는 IOCP 워커 스레드가 맡고, 실제 월드 상태 변경은 GameLogicThread에서 처리하도록 분리했습니다.

서버를 만들면서 가장 중요하게 본 부분은 비동기 환경에서 발생하는 동기화 복잡도를 어떻게 줄일 것인가였습니다. 그래서 복잡한 동기화를 단순하게 하기 위해 MPSC 큐를 도입했고, 여러 워커 스레드가 만들어 내는 작업을 단일 게임 로직 스레드에서 일관성 있게 소비하도록 구성했습니다.

DB는 CPU를 많이 사용하는 계산 작업이라기보다 대기 시간이 큰 I/O 작업이기 때문에, 메인 처리 흐름을 막지 않도록 DB 스레드를 별도로 분리했습니다. 그 결과 네트워크 처리와 게임 로직은 DB 응답을 기다리지 않고 계속 진행할 수 있게 만들었습니다.

설계에서 중요하게 본 부분

MPSC 큐를 도입한 이유

네트워크 완료는 여러 워커 스레드에서 동시에 발생하지만, 플레이어 상태와 NPC 상태, 시야 목록, 전투 판정 같은 월드 데이터는 순서와 일관성이 중요합니다. 이 부분을 여러 스레드가 직접 만지게 두면 락이 많아지고 디버깅 난이도가 급격히 올라갑니다.

그래서 워커 스레드는 작업을 enqueue만 하고, 실제 게임 로직은 GameLogicThread가 단일 소비자로 처리하게 만들었습니다. 이 구조 덕분에 동기화가 단순해졌고, 게임 로직도 훨씬 읽기 쉽게 정리할 수 있었습니다.

DB 스레드를 분리한 이유

로그인, 저장, 신규 계정 생성 같은 DB 작업은 CPU를 오래 점유하는 계산이라기보다 외부 자원 응답을 기다리는 I/O 작업에 가깝습니다. 이 작업을 워커 스레드나 게임 로직 스레드 안에서 처리하면 전체 흐름이 쉽게 막히게 됩니다.

그래서 DB 처리는 별도 큐와 전용 스레드에서 수행하고, 결과만 다시 GameLogicThread로 합류시키는 구조를 선택했습니다. 서버 성능을 유지하면서도 로직 흐름을 깔끔하게 가져가기 위한 선택이었습니다.

이 서버는 락을 많이 쓰는 방식보다, 락이 많이 필요해지지 않도록 흐름을 나누는 방식으로 설계했습니다.
스트레스 테스트 결과로 동시 접속자 6,500명을 기록했고, 이 수치를 기준으로 서버 구조의 방향성을 검증했습니다.

서버 구조

1. IOCP 네트워크 계층
AcceptEx, WSARecv, IOCP를 이용해 접속과 수신을 비동기로 처리했습니다. 워커 스레드는 코어 수 기준으로 생성하고, 완료 통지 중심으로 패킷 흐름을 받도록 구성했습니다.
IOCP AcceptEx Worker Threads
2. GameLogicThread
워커 스레드에서 받은 작업은 MPSC 큐를 통해 GameLogicThread로 전달합니다. 이동, 공격, 시야 갱신, 접속 종료, 로그인 성공 처리 같은 실제 상태 변경은 이 스레드에서 수행합니다.
MPSC Queue Single Consumer World Consistency
3. Timer / AI 계층
공격, 추적, 랜덤 이동, 리스폰, 회복은 TimerThread가 우선순위 큐로 관리합니다. 예정된 시점이 되면 GameLogicThread로 이벤트를 넘겨 게임 로직 흐름 안에서 처리합니다.
Priority Queue Epoch Check NPC AI
4. DB 처리 계층
DBThread와 DBConnectionPool을 분리해 로그인, 저장, 계정 생성 요청을 담당하게 했습니다. DB 응답이 끝난 뒤 필요한 결과만 다시 GameLogicThread로 전달하도록 구성했습니다.
DB Queue Connection Pool Separated I/O

구현한 기능과 특장점

Networking

IOCP 기반 비동기 처리

연결당 스레드를 붙이는 방식이 아니라 완료 통지 기반으로 접속과 수신을 처리해, 많은 접속이 들어와도 구조적으로 확장 가능한 방향을 잡았습니다.

Consistency

게임 상태 변경의 단일 진입점

여러 스레드에서 상태를 직접 바꾸지 않고 GameLogicThread를 통해서만 월드 상태를 변경하게 만들어 전투, 이동, 시야, 리스폰 로직의 일관성을 유지했습니다.

Scalability

섹터 기반 주변 탐색

월드를 섹터로 나누고 인접 섹터만 탐색하도록 구현해, 이동과 시야 갱신 때 모든 오브젝트를 전수 검사하지 않도록 만들었습니다.

Gameplay

A* 기반 NPC 추적과 이벤트형 AI

어그로 NPC가 플레이어를 추적하고, 타이머 기반 이벤트로 공격과 이동을 이어 가도록 구성했습니다. 단순 패킷 처리 서버가 아니라 실제 게임플레이가 돌아가는 서버를 목표로 구현했습니다.

Reliability

세션 토큰과 타이머 에폭

비동기 환경에서 늦게 도착한 예전 작업이 현재 상태를 오염시키지 않도록 세션 토큰과 타이머 에폭을 비교하는 방식으로 오래된 작업을 걸러냈습니다.

Engineering

메모리 풀과 락 디버깅 도구

커스텀 메모리 풀, 락, 데드락 프로파일링 코드까지 함께 구성해 기능 구현뿐 아니라 성능과 안정성 측면도 같이 고려했습니다.

정리

이 서버를 구현하면서 가장 크게 신경 쓴 부분은 네트워크, 게임 로직, 타이머, DB가 서로 다른 성격의 작업이라는 점이었습니다. 각 계층이 가장 잘하는 역할만 맡도록 분리하고, 실제 월드 상태 변경은 하나의 흐름으로 모아서 관리하는 방향으로 구조를 잡았습니다.

그 과정에서 MPSC 큐를 도입해 동기화 복잡도를 낮췄고, DB는 CPU를 쓰는 작업이 아니라 기다림이 큰 I/O라는 점을 고려해 별도 스레드로 분리했습니다. 결과적으로 비동기 서버에서 자주 문제가 되는 락 경합, 흐름 꼬임, 블로킹 병목을 구조적으로 줄이는 데 집중한 프로젝트였습니다.

스트레스 테스트에서 동시 접속자 6,500명을 기록했고, 이 결과를 통해 설계 방향이 실제 부하에서도 유효하다는 점을 확인할 수 있었습니다.

이 프로젝트는 IOCP를 적용하는 데서 끝난 것이 아니라, 그 위에서 게임 서버 구조를 어떻게 안정적으로 운영할지까지 고민한 결과물입니다.
